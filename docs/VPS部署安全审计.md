# 在 VPS 上部署 Cowrie 蜜罐的安全审计

面向：Ubuntu 24.04 LTS，DigitalOcean / Vultr / Linode 一类 VPS，蜜罐暴露公网以捕获真实攻击。

学校不建议在 VPS 跑蜜罐，核心原因就是下面这些风险。本文逐条给出“会出什么问题 + 怎么解决”，
并标注哪些已由 `defense/deploy_defense.sh` 自动处理。

---

## 结论先行

可以在 VPS 上跑，但蜜罐是“故意被攻破”的服务，等于主动把一台机器放到枪口上。
安全的重点不是“别被打”，而是**把被打之后的影响关在蜜罐里**：真实管理面要和蜜罐彻底分开，
出站要能兜底，日志要能外带，服务商投诉要能应对。手工部署（不用 .ova）正是为了把这些加固做进去。

---

## 一、主机自身暴露面

| 问题 | 风险 | 解决 | 脚本是否自动 |
|------|------|------|------|
| 真实 sshd 和蜜罐挤在 22 | 真实攻击打 22 会进你的真实 sshd；或你和攻击者流量混在一起 | 管理 SSH 移到 2022，22 重定向给 Cowrie | 是（两阶段） |
| 密码登录开着 | 管理口被爆破 | `PasswordAuthentication no`，仅密钥；`PermitRootLogin prohibit-password` | 是 |
| 其他默认服务在监听 | 多一个服务多一个洞 | 部署后 `ss -tulnp` 核对，只留管理端口 + 蜜罐 | 否，手动核对 |
| 防火墙放行过宽 | 未知端口被探测利用 | ufw 默认拒绝入站，只放行 2022 / 22 / 2222 | 是 |

> 自己动手：装完后务必 `ss -tulnp` 看一眼还有没有别的端口在听（比如云厂商镜像预装的监控 agent）。

## 二、把蜜罐关住（最关键）

Cowrie 是中交互蜜罐，攻击者的命令跑在**伪 shell**里，不会真在你主机上执行——这是它天然的安全边界。
但仍有两个真实风险：

1. **下载的恶意样本**。攻击者常 `wget/curl` 投放脚本，Cowrie 会把这些文件存到 `var/lib/cowrie/downloads/`。
   这些是**真实恶意文件**。解决：确认它们永远不被执行（Cowrie 不执行，别自己手贱去跑）；
   目录权限隔离；分析完要么妥善留存要么清理；别用 root 去碰。

2. **出站流量 = 最大风险**。真正怕的是这台机器被当成跳板去连 C2、挖矿、打 DDoS。
   Cowrie 本身不会真发起这些，但要兜底：
   - 进程加固：systemd 单元已加 `NoNewPrivileges` / `ProtectSystem=strict` / `PrivateTmp` /
     `CPUQuota` / `LimitNOFILE`，即使有人突破也难提权、难把带宽打满。**脚本已做。**
   - 出站收紧：理想是默认拒绝出站、只放行 DNS + apt + 你的日志外送 + ip-api 查询。
     脚本**没有**强制切断出站（怕把机器自己弄死），见下方“可选：收紧出站”。

### 可选：收紧出站（手动，验证后再做）

```bash
sudo ufw default deny outgoing
sudo ufw allow out 53          # DNS
sudo ufw allow out 80,443/tcp  # apt / ip-api 查询 / 时间同步
# 注意：切断出站前先确认 apt、DNS、你的 scp 备份都在放行名单里，否则机器会“失联”
```

## 三、数据与法务（VPS 特有）

- **服务商条款（AUP）**：DigitalOcean / Vultr / Linode 对蜜罐相对宽容，但**一定会把 abuse 投诉转给你**。
  投诉可能来自：你的 IP 在扫描别人（其实多半是误报，但也要能解释）、或样本下载触发了对端告警。
  部署前读一遍服务商 AUP；收到 abuse 邮件**务必及时回应**（说明是学术蜜罐、已隔离），否则可能被停机。
- **你在采集真实攻击者的真实数据**（IP、凭据、payload）。分析用途没问题，但：不要拿这些去“反打”，
  不要随意转发样本，遵守当地法律。学术研究范围内是正当的。
- **日志外带**：VPS 随时可能被服务商停机或被攻击者盯上。日志不要只存在机器上，
  定期 `scp` 到别处（或配 Cowrie 的 output 插件发到你另一台机器）。

## 四、运维与监控

- **auditd**：脚本已装。用它记录**你自己**的管理登录，便于把“你”和“攻击者”区分开。
- **磁盘**：Cowrie 下样本 + json 日志增长快，监控 `df -h`，别把盘写满导致 Cowrie 停。
- **可重建**：部署脚本本身就是“基础设施即代码”，机器被搞坏直接重装 + 跑脚本即可。做个快照更稳。

---

## 五、为什么手工复现比 .ova 好（针对本次）

1. VPS 给的是云镜像，**根本导入不了 VirtualBox 的 .ova**，手工装是唯一可行路径。
2. 手工装能把上面的加固（端口分离、ufw、systemd 加固、auditd）直接写进流程，`.ova` 是个黑盒改不动。
3. 可复现、可版本控制：`deploy_defense.sh` 一跑就能在另一台 VPS 重建同样环境。

## 六、部署顺序速查

```bash
# 防守机（蜜罐 VPS）
#  0. 先确保你的 SSH 公钥已在服务器上（否则第一阶段关掉密码登录后进不去）
#  1. 第一阶段：装 Cowrie + 工具 + 加固，管理口加到 2022（22 不动）
sudo ./defense/deploy_defense.sh
#  2. 另开终端验证： ssh -p 2022 user@蜜罐IP   能进再继续
#  3. 第二阶段：把 22 切给蜜罐，开始抓真实攻击
sudo ./defense/deploy_defense.sh --cutover

# 攻击机（另一台 VPS）
sudo ./attack/deploy_attack.sh
./attack/simulate_attack.sh 蜜罐公网IP 22
```

> 最后再强调一次顺序上的坑：第一阶段会关掉密码登录只留密钥。**跑之前务必先把公钥传上去**，
> 否则会把自己锁在门外。
