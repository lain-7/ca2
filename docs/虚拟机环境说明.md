> 记录对象：课程提供的 `UbuntuCowrie.ova`（VirtualBox 镜像）
> 迁移目标：KVM / libvirt
> 记录日期：2026-10-26

## 一、我们做了什么，为什么这样做

### 1.1 课程提供的是 VirtualBox 镜像

课程材料提供了两个 `.ova` 文件（VirtualBox 导出格式）：

| 文件 | 用途 | 大小 |
|---|---|---|
| `UbuntuCowrie.ova` | 蜜罐服务器（VM A） | 4.2 GB |
| `UbuntuClient.ova` | 攻击者客户端（VM B） | 4.0 GB |

配套的《Cowrie Setup Guide》要求在 VirtualBox 中导入，并配置为**桥接网卡（Bridged Adapter）**。

### 1.2 我们改用 KVM

小组成员均为 Linux 用户，不使用图形界面。VirtualBox 的导入、图形化配置对命令行环境不友好，因此我们选择用 **KVM / libvirt** 运行同一套镜像。

**这不违反作业要求。** 作业的硬性约束只有两条：

> - 严禁使用云服务部署虚拟机（Do not deploy the VM using cloud services）
> - 不得将蜜罐公开暴露到互联网（do not make it publicly accessible）

我们用本地 KVM 运行，网络是 libvirt 的**隔离 NAT**，比课程要求的桥接模式**更封闭**——蜜罐完全无法从外部网络访问。

## 二、为适配 KVM 对镜像做的改动

### 2.1 磁盘格式转换：VMDK → qcow2

`.ova` 内部是 VMDK 格式的虚拟磁盘（VirtualBox 专用）。KVM 虽然能直接读 VMDK，但为了性能和快照支持，我们转换为 qcow2：

```bash
tar -xf UbuntuCowrie.ova          # 解出 .ovf 和 .vmdk
qemu-img convert -O qcow2 UbuntuCowrie-disk001.vmdk cowrie.qcow2
```

**原始 OVA 文件未做任何修改**，转换是只读操作。

### 2.2 修复文件系统（因为镜像不是正常关机导出的）

第一次尝试挂载磁盘时报错：

```
EXT4-fs (dm-0): error loading journal
JBD2: journal recovery failed
```

原因：镜像导出时系统未正常关机，ext4 日志处于未提交状态。我们以读写方式挂载副本并执行 `e2fsck` 修复：

```bash
e2fsck -f -y /dev/ubuntu-vg/ubuntu-lv     # 根分区
e2fsck -f -y /dev/nbd0p2                  # /boot
```

修复后文件系统正常，两次 fsck 的 `FILE SYSTEM WAS MODIFIED` 提示都属于预期的元数据修正（inode 计数等），不影响数据。

### 2.3 ⭐ 关键改动：netplan 里写死了 VirtualBox 的 MAC 地址

**这是最重要的一处改动，不改的话虚拟机在 KVM 下会没有网络。**

原镜像的 `/etc/netplan/00-installer-config.yaml` 内容：

```yaml
# This is the network config written by 'subiquity'
network:
  ethernets:
    enp0s3:
      dhcp4: true
      dhcp6: true
      match:
        macaddress: 08:00:27:86:74:21      # ← 问题在这里
      set-name: enp0s3
  version: 2
```

**问题：**

`match.macaddress` 要求网卡的 MAC 地址**必须**是 `08:00:27:86:74:21` 才会应用这份配置。这个 MAC 是 VirtualBox 为这块虚拟网卡生成的（`08:00:27` 是 VirtualBox 的 OUI 前缀）。

一旦换了虚拟化平台（KVM、VMware、或任何新导入的 VirtualBox 实例），网卡 MAC 会变，**netplan 就匹配不到任何网卡**：

- 网卡不会被配置
- 拿不到 IPv4 地址
- 虚拟机完全没有网络

**改法：**

备份原文件，改为按**接口名前缀**匹配，不再依赖 MAC：

```yaml
# Rewritten for KVM/libvirt: match by interface name instead of the
# VirtualBox MAC address, so DHCP works regardless of hypervisor.
network:
  version: 2
  ethernets:
    primary:
      match:
        name: "en*"                        # ← 匹配 enp0s3 / enp1s0 / ens33 等
      dhcp4: true
      dhcp6: true
```

原文件备份为 `00-installer-config.yaml.vboxbak`，随时可以还原。

**效果：** 虚拟机换到 KVM 后网卡自动重命名为 `enp1s0`（KVM 的 virtio 网卡命名），并正常通过 DHCP 拿到 `192.168.122.252`。

### 2.4 用直接内核引导启动（绕过 GRUB）

第一次启动时，我们没有走 GRUB，而是让 libvirt 直接加载内核和 initrd：

```xml
<os>
  <type arch='x86_64' machine='q35'>hvm</type>
  <kernel>/var/lib/libvirt/images/cowrie-vmlinuz</kernel>
  <initrd>/var/lib/libvirt/images/cowrie-initrd</initrd>
  <cmdline>root=/dev/mapper/ubuntu--vg-ubuntu--lv ro console=ttyS0,115200</cmdline>
</os>
```

这样做的原因：原镜像的 GRUB 配置没有针对串口控制台优化，直接指定内核参数可以确保 `console=ttyS0` 生效，便于无图形界面调试。

**这一步不是必需的**，虚拟机正常运行后可以改回标准磁盘引导。记录在此以便复现。

## 四、网络架构对比

### 课程指南建议的配置（VirtualBox 桥接）

```
[家庭路由器] ── [宿主机 Wi-Fi]
                      │
                      └── [VirtualBox 桥接]
                            ├── Cowrie VM  (与宿主机同一网段)
                            └── Client VM  (与宿主机同一网段)
```

桥接模式下，虚拟机直接暴露在宿主机所在的局域网中。

### 我们实际使用的配置（KVM NAT）

```
[宿主机 Arch Linux]
      │
      └── virbr0  192.168.122.1/24  (libvirt 默认 NAT 网络)
            ├── Cowrie VM   192.168.122.252   [仅内网可达]
            └── (Client VM 待建)
```

**差异与评估：**

| 方面 | 桥接（课程建议） | NAT（我们的做法） |
|---|---|---|
| 局域网内其他设备能否访问蜜罐 | 能 | **不能** |
| 蜜罐能否访问公网 | 能 | 能（经 NAT 转发） |
| 是否满足"不得公开暴露到互联网" | 取决于网络环境 | **天然满足** |
| 是否便于隔离测试 | 需要额外防火墙规则 | **天然隔离** |

**结论：** NAT 模式在**隔离性上严格优于**桥接模式，更符合作业"受控环境"的要求。作业评分表对网络的要求是"两台 VM 均正确配置、网络连通"，NAT 完全满足。

## 五、环境可达性实测

在改造完成后，我们对网络隔离做了实测（详细数据见 `docs/蜜罐识别器设计与检测报告.md` 第九章）：

| 目标 | 结果 |
|---|---|
| 宿主机 → 蜜罐 `192.168.122.252:2222` | ✅ 通 |
| 蜜罐 → 公网 `example.com:80` | ✅ 通 |
| 蜜罐 → 宿主机 `192.168.122.1:22` | ❌ 不通（firewalld 拦截） |
| 蜜罐 → 宿主机所在局域网 `192.168.1.x` | ❌ 不通 |
| 蜜罐 → Docker 网段 `172.17.0.1` | ❌ 不通 |

**重要提醒：** 这种隔离是**隐式**的——依赖宿主机 firewalld 的默认策略，而不是虚拟机自身的显式规则。一旦宿主机的防火墙规则变化，这层保护就会消失，而虚拟机内部完全无感知。

如果需要更强的保证，建议在 libvirt 的 `nwfilter` 里**显式声明**出向规则，把"碰巧安全"变成"声明安全"。

## 六、复现步骤

从原始 OVA 完整复现我们的环境：

```bash
# 1. 解压 OVA
mkdir -p inspect && cd inspect
tar -xf ../UbuntuCowrie.ova

# 2. 转换为 qcow2
qemu-img convert -O qcow2 UbuntuCowrie-disk001.vmdk cowrie.qcow2

# 3. 修复文件系统（镜像非正常关机）
sudo modprobe nbd max_part=16
sudo qemu-nbd -f qcow2 -c /dev/nbd0 "$PWD/cowrie.qcow2"
sudo vgchange -ay ubuntu-vg
sudo e2fsck -f -y /dev/ubuntu-vg/ubuntu-lv
sudo e2fsck -f -y /dev/nbd0p2

# 4. 挂载并修改 netplan（关键步骤）
sudo mount /dev/ubuntu-vg/ubuntu-lv /mnt/x
sudo cp /mnt/x/etc/netplan/00-installer-config.yaml{,.vboxbak}
# 写入按 name 匹配的版本（见 2.3 节）
sudo umount /mnt/x
sudo vgchange -an ubuntu-vg
sudo qemu-nbd -d /dev/nbd0

# 5. 放入 libvirt 镜像目录
sudo cp cowrie.qcow2 /var/lib/libvirt/images/
sudo chown root:root /var/lib/libvirt/images/cowrie.qcow2

# 6. 用 libvirt 定义并启动（XML 见 2.4 节）
sudo virsh -c qemu:///system define cowrie.xml
sudo virsh -c qemu:///system start cowrie
```

连接方式：

```bash
# 系统管理（真实 sshd）
ssh ubuntucowrie@192.168.122.252        # 密码 123456

# 蜜罐（Cowrie）
ssh root@192.168.122.252 -p 2222        # 任意密码均可登录
```

## 七、快照

在开始任何改造之前，我们创建了外部快照：

```bash
virsh -c qemu:///system snapshot-create-as cowrie \
  baseline-2026-10-26 "clean state: KVM-converted, netplan fixed, fsck'd, Cowrie 3.0.13" \
  --disk-only --atomic
```

| 项 | 值 |
|---|---|
| 快照名 | `baseline-2026-10-26` |
| 类型 | external（原始磁盘保留为只读基底） |
| 当前盘 | `/var/lib/libvirt/images/cowrie.baseline-2026-10-26` |
| 基底盘 | `/var/lib/libvirt/images/cowrie.qcow2` |

回滚到改造前：

```bash
virsh -c qemu:///system snapshot-revert cowrie baseline-2026-10-26
```

## 八、已知问题

| 问题 | 影响 | 计划 |
|---|---|---|
| Cowrie 未配置开机自启 | VM 重启后 2222 端口不监听，需手动启动 | 建议写 systemd unit |
| `cowrie start` 依赖 venv 已激活 | 直接调用 `cowrie-env/bin/cowrie` 会因 PATH 里找不到 `twistd` 而失败 | 未修（可写全路径规避） |
| 宿主机 `qemu.conf` 未配置为以当前用户运行 | 虚拟机镜像必须放在 `/var/lib/libvirt/images`（root 所有） | 未改（改动需 root） |
| 真实 sshd 使用弱密码 `123456` | 见下方说明 | 课程预设，保留 |

### 关于真实 sshd 的说明

虚拟机内同时运行着：

- **Cowrie 蜜罐**（2222 端口）—— 模拟的 SSH 服务
- **真实 OpenSSH**（22 端口）—— 课程镜像自带，用于系统管理

真实 sshd 的账号 `ubuntucowrie` / `123456` 是课程预设的。在本次实验中：

- **它不可从外部访问**——虚拟机在 libvirt NAT 后，22 端口外部完全不可达
- **它被用作对照组**——我们的检测器用它对验证「不会把真实系统误判为蜜罐」
- **它构成真实风险**——如果虚拟机被暴露到可达网络，这个弱密码账号属于 sudo 组，等同于直接交出 root

**在正式部署中，这个真实 SSH 服务应当关闭或限制为仅密钥登录。** 我们保留它是为了实验对照，这一点在报告中已明确记录。
