## 一、这份文档解决什么问题

### 1.1 背景

本组作业需要在 Ubuntu 虚拟机上部署 Cowrie SSH 蜜罐，模拟攻击、分析日志。在部署过程中，一个自然的问题浮现出来：

> **攻击者能不能看出来这是一个蜜罐？**

这个问题在真实的安全运营中很重要。蜜罐的价值取决于攻击者是否相信它是真的服务器。一旦被识破，攻击者会：

- 立刻停止操作，不留下有价值的 TTP 信息；
- 反向利用蜜罐，向防守方投喂虚假情报；
- 甚至把蜜罐当作攻击防守方的跳板（虽然对 Cowrie 不成立，见第九章）。

因此，**量化"这个蜜罐有多容易被识破"是蜜罐部署的必修课**。

### 1.2 本项目做了什么

本项目实现了 `honeypot_detect.py`，一个主动式的蜜罐识别器。它的工作方式是：

1. 像普通 SSH 客户端一样连接目标；
2. 在协议层、认证层、文件系统层、命令行为层、终端行为层做一系列探测；
3. 收集观测结果，与"真实 Linux 系统应有的表现"对比；
4. 输出一个 0–100 的**暴露指数**和判定结论。

它**只做被动探测**：所有操作都是只读的（`ls`、`cat`、`head`、`uname` 等），不修改目标任何状态，不包含利用、上传、提权、持久化、横向移动逻辑。

### 1.3 为什么不直接写"检测到 Cowrie"

因为**识别 Cowrie 本身没有工程价值**。Cowrie 的安装路径、进程名、端口都可以改。有价值的是识别"这个系统不是它声称的样子"这一**结构性矛盾**。

本脚本的所有检测项都基于"模拟与真实的差距"，而不是"Cowrie 的某个已知字符串"。所以：

- 它能识别改过名的 Cowrie；
- 它能识别其他中等交互蜜罐（Kippo、Heralding 等）的一部分特征；
- 它的每一条检测项都能说明"为什么这不可能出现在真实系统上"。

## 二、检测原理：为什么蜜罐可以被识别

### 2.1 蜜罐的两种实现路径，两种破绽

**高交互蜜罐**（如 T-Pot 的部分组件）运行真实系统，攻击者的一切操作都是真的。这类蜜罐伪装的破绽主要在于 **网络位置**和**业务逻辑**（一台"生产数据库"却没有任何业务流量），而不在系统内部。

**中等交互蜜罐**（Cowrie 属于这一类）不运行真实系统，而是用代码**模拟** Linux 的行为：

- 假文件系统：用一个 pickle 序列化的文件树代替真实磁盘
- 假 shell：用 Python 模块逐条实现 `ls`、`cat`、`wget` 等命令
- 假认证：用一个规则表决定哪些密码"登录成功"

**模拟必然有偏差，偏差就是指纹。** 这是本项目所有检测项的共同来源。

### 2.2 四个层次的偏差

| 层次 | 偏差来源 | 可修复性 |
|---|---|---|
| 协议层 | SSH 实现不是 OpenSSH，算法集和能力集不同 | **极难** —— 需要换掉整个 SSH 栈 |
| 认证层 | 设计使然：必须接受任意密码，否则攻击者进不来 | **不可修复** —— 修了就不是蜜罐了 |
| 文件系统层 | 假文件系统是从快照生成的，内部数据互相矛盾 | **容易** —— 重新生成 fs.pickle 即可 |
| 命令行为层 | 简化解析器无法覆盖真实命令的全部语法 | **中等** —— 需要逐个补全命令实现 |

这个表格直接决定了第八章"如何把指数降到最低"的可行边界。

## 三、五层检测模型

### 3.1 协议层：不登录就能看出的东西

**核心思路**：SSH 握手阶段，双方会交换各自的"能力清单"（`SSH_MSG_KEXINIT`）。真实 OpenSSH 提供的算法集有明确的年代特征，而 Cowrie 底层用的是 Twisted 的 SSH 实现，算法集停留在很多年前。

本项目直接读原始 TCP 包，自己解析 `SSH_MSG_KEXINIT`，不依赖任何库的内部实现。这样做有两个好处：

1. 完全避开认证流程，日志里只留一条连接记录；
2. 不受 paramiko 版本差异影响（paramiko 5.x 会在握手后清空 `remote_kex_init`）。

**检测项**：

| 检测项 | 依据 | 依据的 OpenSSH 版本 |
|---|---|---|
| 未提供任何 AEAD 密码 | OpenSSH 6.5+ 提供 AES-GCM，6.7+ 提供 chacha20-poly1305 | 2014 年起 |
| 提供已废弃的 CBC 密码 | OpenSSH 8.2 起默认禁用全部 CBC | 2020 年起 |
| 未提供 Encrypt-then-MAC | OpenSSH 6.2+ 支持，7.2+ 默认启用 | 2016 年起 |
| 提供已被移除的 hmac-md5 | OpenSSH 8.8 起从默认集移除 | 2021 年起 |
| host key 仅提供旧式 ssh-rsa | OpenSSH 7.2+ 用 rsa-sha2-*，8.8 起禁用裸 ssh-rsa | 2021 年起 |
| 不支持 exec 通道 | 所有 OpenSSH 都支持 `ssh host '命令'` | —— |

### 3.2 认证层：它接受什么密码

**核心思路**：真实系统不接受无意义的随机密码。Cowrie 的 `UserDB` 默认规则是"root 除少数黑名单外全放行"，所以一个 24 位高熵随机密码能登录成功，就几乎可以单独定案。

这一条的特殊性在于：**它不可修复**。蜜罐的本质是让攻击者进来，所以必须接受攻击者猜的密码。如果改成只接受正确密码，攻击者就进不来，蜜罐也就失效了。

### 3.3 文件系统层：假文件系统的内部矛盾

**核心思路**：Cowrie 的 `fs.pickle` 是从某个真实系统（实际上是一个 Docker 容器）里用 `bin/createfs` 抓取的快照。快照只保存元数据和少量文件内容，且抓取后**不会再更新**。这导致三类矛盾：

1. **数据源之间不同步**：提示符主机名来自 `[honeypot] hostname` 配置，`/etc/hostname` 来自 pickle，两者独立
2. **内容缺失**：只有路径没有内容的文件（如 `sshd_config` 为空）
3. **快照痕迹**：批量条目共享同一个 mtime；容器标记文件被一起抓进来

**检测项**：

| 检测项 | 原理 |
|---|---|
| `/etc/os-release` 为空或类型异常 | 所有现代发行版都要求它是非空普通文件 |
| 主机名三个来源矛盾 | 提示符 / `hostname` 命令 / `/etc/hostname` 应完全相同 |
| 存在容器标记 | `/.dockerenv`、`/proc/docker` 只存在于 Docker 容器内 |
| `/etc/ssh/sshd_config` 为空 | 运行 SSH 服务的系统必然有非空配置 |
| 时间戳高度雷同 | 真实系统的 mtime 分散在数年，去重率接近 100% |

### 3.4 命令行为层：简化解析器的痕迹

**核心思路**：Cowrie 用 Python 模块逐个实现 Unix 命令。每个实现都只覆盖常见用法，遇到真实命令支持但模拟器不支持的语法就会暴露。

**检测项**：

| 检测项 | 原理 |
|---|---|
| `head -3` / `tail -2` 报 invalid option | POSIX 与 GNU coreutils 都支持数字简写 |
| `df` / `sed` 报 Exec format error | coreutils 与 POSIX 必备命令，不可能无法执行 |
| `top` 报 E82 | 模拟器走进未处理路径 |
| 缺少 `ss` / `ip` / `systemctl` | iproute2 自 2001 年、systemd 自 2015 年起是默认组件 |
| `ifconfig` 显示 eth0 | net.ifnames 自 2015 年起改为可预测网卡名 |
| `uptime` 异常短 | Cowrie 的 uptime 从进程启动算，不是从系统启动算 |

### 3.5 终端行为层：shell 的输出特征

**核心思路**：真实 bash 会发送一系列终端控制序列（bracketed paste、OSC 标题设置、会话标记）。Cowrie 的模拟 shell 只发送最基本的提示符，并额外插入了自己的转义序列。

**检测项**：

| 检测项 | 原理 |
|---|---|
| 出现 `ESC[4l` / `ESC[4h` | Cowrie 在每条输出前后插入下划线开关，真实 bash 不会 |
| 缺少 bracketed paste 序列 | 现代 bash（5.0+）默认启用 `ESC[?2004h` |

## 四、评分模型

### 4.1 三级证据强度

每条检测项有一个强度标签和一个分值：

| 强度 | 含义 | 判定规则 |
|---|---|---|
| **决定性**（DECISIVE） | 真实系统上不可能出现的特征 | 单条命中即可定案 |
| **强信号**（STRONG） | 真实系统上出现概率极低 | 2 条以上命中即判定 |
| **弱信号**（WEAK） | 单独看可能只是配置差异 | 需多条同时命中 |

### 4.2 计分规则

```
暴露指数 = Σ(命中项的权重)
```

但有三个修正：

1. **决定性项兜底**：任一决定性项命中，指数至少 70（保证判定为蜜罐）
2. **防误报**：若无决定性项命中，且只有 1 条强信号 + 至多 1 条弱信号命中，指数上限压到 25
3. **上限**：100

### 4.3 判定区间

| 指数 | 判定 | 含义 |
|---|---|---|
| ≥ 60 | 确定是蜜罐 | 发现结构性矛盾，不可能是真实系统 |
| 30–59 | 高度可疑 | 多处异常，大概率是模拟环境 |
| 10–29 | 存在异常 | 建议人工复核 |
| < 10 | 未发现明显特征 | 伪装良好或确实真实 |

**注意**：指数不是"漏洞严重性"，而是"被识破的容易程度"。指数越高，攻击者越容易看出这是蜜罐。

## 五、使用说明

### 5.1 环境要求

```bash
# 只需要 paramiko，其余均为 Python 标准库
pip install paramiko

# Python 3.9+
```

### 5.2 基本用法

```bash
# 完整检测（推荐）
python3 honeypot_detect.py --host 192.168.122.252 --port 2222

# 只看结论，不看证据
python3 honeypot_detect.py --host 192.168.122.252 --port 2222

# 带证据输出（终端里能看到每条检测项的实际观测值）
python3 honeypot_detect.py --host 192.168.122.252 --port 2222 --verbose

# JSON 输出（便于脚本处理、前后对比）
python3 honeypot_detect.py --host 192.168.122.252 --port 2222 --json

# 只做协议层 + 认证层，不进入 shell（最隐蔽的探测方式）
python3 honeypot_detect.py --host 192.168.122.252 --port 2222 --passive

# 导出完整证据到文件
python3 honeypot_detect.py --host 192.168.122.252 --port 2222 --evidence evidence.json

# 指定凭据
python3 honeypot_detect.py --host X --port 22 --user ubuntucowrie --password 'yourpass'
```

### 5.3 参数说明

| 参数 | 默认值 | 说明 |
|---|---|---|
| `--host` | 必填 | 目标 IP 或主机名 |
| `--port` | 2222 | SSH 端口 |
| `--user` | root | 登录用户名 |
| `--password` | password | 登录密码 |
| `--timeout` | 15.0 | 连接超时秒数 |
| `--json` | 关 | 以 JSON 输出 |
| `--evidence FILE` | 无 | 把完整证据写入指定文件 |
| `--passive` | 关 | 只做协议层与认证层，不进入 shell |
| `--no-color` | 关 | 禁用彩色输出 |
| `--verbose` | 关 | 终端输出中包含证据与说明 |

### 5.4 退出码

| 退出码 | 含义 |
|---|---|
| 0 | 已识别为蜜罐（指数 ≥ 60） |
| 1 | 未识别（指数 < 60） |
| 2 | 连接失败或参数错误 |

便于在 CI 或批量脚本中使用：

```bash
if python3 honeypot_detect.py --host $H --port $P --json > /dev/null; then
    echo "检测到蜜罐"
fi
```

### 5.5 从宿主机迁移到 VM B

脚本本身不依赖任何特定环境，复制过去直接运行：

```bash
scp honeypot_detect.py ubuntuclient@<vm-b-ip>:~/
ssh ubuntuclient@<vm-b-ip> 'sudo apt install -y python3-paramiko && python3 ~/honeypot_detect.py --host <蜜罐IP> --port 2222'
```

## 六、检测结果

### 6.1 对照组设计

为了验证检测器**不会误报**，本项目同时测试了两个目标：

| 目标 | 说明 |
|---|---|
| `192.168.122.252:2222` | Cowrie 蜜罐（待检测对象） |
| `192.168.122.252:22` | 同一台 VM 上的真实 OpenSSH（对照组） |

**为什么这个对照组特别有价值**：两台是**同一个 IP、同一台物理机、同一个网段**。唯一的变量是"服务端是 Cowrie 还是 OpenSSH"。如果检测器只是靠"IP 可疑"、"端口非标准"这类外部因素判断，两组结果会一样；如果它真的在分析系统行为，两组会完全不同。

### 6.2 结果对照

| 指标 | Cowrie :2222 | 真实 sshd :22 |
|---|---|---|
| **暴露指数** | **100 / 100** | **10 / 100** |
| 判定结论 | 确定是蜜罐 | 存在异常，建议人工复核 |
| 决定性项命中 | 4 / 4 | 0 / 4 |
| 强信号命中 | 13 / 13 | 0 / 12 |
| 弱信号命中 | 6 / 7 | 1 / 8 |

**结论**：检测器能清晰区分两者，且对真实系统几乎没有误报。

### 6.3 真实 sshd 上的那 10 分是什么

真实 sshd 唯一命中的是"系统运行时间异常短"（+10）。这是**真实的观察**：VM 在 10:08 左右启动，测试在 10:31 进行，`uptime` 显示 23 分钟。

这不是误报，是**正确识别了一个可疑状态**。刚启动的服务器确实可疑，只是这个信号单独不足以定案——这正是把它归为"弱信号"（权重 10）而不是"强信号"的原因。

## 七、每条检测项的详细说明

### 7.1 决定性项

#### `auth.accepts_random_password`（+30）

**检测方法**：用一个 24 位高熵随机密码登录 `root`。

```python
rand_pw = "".join(random.choices(string.ascii_letters + string.digits + "!@#$%^&*", k=24))
```

**实测结果**：

```
Cowrie  : ACCEPTED  root / 'Zq9$xK!mP2vR'
真实sshd: REJECTED  -> AuthenticationException
```

**原理**：Cowrie 的 `core/auth.py` 里定义了内置规则：

```python
_USERDB_DEFAULTS = [
    "root:x:!root",       # 拒绝密码 root
    "root:x:!123456",     # 拒绝密码 123456
    "root:x:!/honeypot/i",# 拒绝含 honeypot 的密码
    "root:x:*",           # 其余全部放行
    "phil:x:*",
    "phil:x:fout",
]
```

`root:x:*` 意味着 root 除三条黑名单外**全部放行**。所以任何随机密码都能登录。

**为什么是决定性**：真实系统不可能接受无意义的随机密码。这一条单独就能定案。

**可修复性**：**不可修复**。这是蜜罐的设计前提。

---

#### `fs.os_release_invalid`（+25）

**检测方法**：

```bash
cat /etc/os-release       # 返回空
ls -ld /etc/os-release    # 返回 -rw-r--r-- ... 267 ... /etc/os-release
```

**矛盾点**：`ls` 说这是一个 267 字节的普通文件，`cat` 却读不出任何内容。

**原理**：Cowrie 的 `fs.pickle` 里这个路径的数据结构有误。用 `dumpfs` 导出能看到它的类型标记是 `T_DIR`（目录），但 `ls.py` 把它当普通文件渲染，于是显示了一个从别处继承来的大小值。

**为什么是决定性**：`/etc/os-release` 是 systemd 规范的强制要求，所有现代发行版都必须提供非空内容。这个矛盾在真实系统上不可能出现。

**可修复性**：**容易**。重新生成 fs.pickle 时正确填充内容即可。

---

#### `cmd.df_broken_binary`（+20）/ `cmd.sed_broken_binary`（+15）

**检测方法**：

```bash
df -h
sed -n 1p /etc/passwd
```

**实测结果**：

```
-bash: /usr/bin/df: cannot execute binary file: Exec format error
-bash: /usr/bin/sed: cannot execute binary file: Exec format error
```

**原理**：Cowrie 对**未实现**的命令（`commands/` 目录里没有对应 Python 模块的）会返回一个"通用二进制"内容。当攻击者真的去执行它时，内核（在模拟层）判定这不是有效的可执行文件，于是报 `Exec format error`。

**为什么是决定性**：`df` 属于 coreutils，`sed` 是 POSIX 必备工具。任何 Linux 发行版都不可能缺少它们，更不可能"存在但无法执行"。

**可修复性**：**中等**。需要为这些命令补充真实的 Python 实现。

---

### 7.2 强信号

#### `proto.no_exec_channel`（+18）

**检测方法**：尝试 `ssh host 'true'`（SSH exec 通道）。

**实测结果**：

```
Cowrie  : paramiko.ssh_exception.SSHException: Channel closed.
真实sshd: exec_command 成功，rc=0
```

**原理**：SSH 协议有两个通道类型：

- `session` + `shell` 请求 → 交互式终端（`ssh host`）
- `session` + `exec` 请求 → 执行单条命令（`ssh host '命令'`）

Cowrie 只实现了前者。这是 Twisted SSH 实现的结构限制。

**为什么重要**：这是**协议层的结构性缺陷**，不是配置问题。要修复必须换掉整个 SSH 栈。

**可修复性**：**极难**。

---

#### `proto.no_aead_cipher`（+16）/ `proto.legacy_cbc`（+14）/ `proto.no_etm_mac`（+14）/ `proto.md5_mac`（+12）

**检测方法**：直接读原始 TCP，解析服务端的 `SSH_MSG_KEXINIT` 包。

**实测对照**：

```
Cowrie :2222
  enc = aes128-ctr, aes192-ctr, aes256-ctr, aes256-cbc, aes192-cbc,
        aes128-cbc, 3des-cbc, cast128-cbc
  mac = hmac-sha2-512, hmac-sha2-384, hmac-sha2-256, hmac-sha1, hmac-md5

真实 sshd :22
  enc = chacha20-poly1305@openssh.com, aes128-gcm@openssh.com,
        aes256-gcm@openssh.com, aes128-ctr, aes192-ctr, aes256-ctr
  mac = umac-64-etm@openssh.com, umac-128-etm@openssh.com,
        hmac-sha2-256-etm@openssh.com, hmac-sha2-512-etm@openssh.com, ...
```

**四条差异**：

| 特征 | Cowrie | OpenSSH | 分界线 |
|---|---|---|---|
| AEAD 密码 | 无 | 有 GCM / chacha20 | 2014 年 |
| CBC 密码 | 提供 | 已默认禁用 | 2020 年 |
| ETM MAC | 无 | 有 | 2016 年 |
| hmac-md5 | 提供 | 已移除 | 2021 年 |

**为什么是强信号**：这四条合起来描绘出一个"2013 年前后"的 SSH 实现。而 banner 却声称是 `OpenSSH_9.2p1 Debian-2+deb12u3`（2023 年的版本）。**banner 与算法集的年代矛盾**，本身就是铁证。

**可修复性**：**极难**。算法集由 Twisted（或 paramiko）的 SSH 栈决定，修改 `cowrie.cfg` 的 `ciphers`/`macs` 只能**减少**宣告的算法，不能**增加** Twisted 不支持的算法。所以真正的修复是替换 SSH 实现层。

---

#### `term.underline_escape`（+15）

**检测方法**：观察交互式 shell 原始字节流。

**实测结果**：

```
Cowrie  : b'whoami\r\n\x1b[4lroot\r\n\x1b[4hroot@ubuntu-server:~# '
真实sshd: b'whoami\r\n\x1b[?2004l\r\x1b]3008;start=...\x1b\\ubuntucowrie\r\n...'
```

**原理**：Cowrie 在每条命令输出前后插入 `ESC[4l`（关闭下划线）和 `ESC[4h`（开启下划线）。这是 Cowrie 用来遮盖提示符内部状态变化的技巧，但真实 bash 不会主动发送这两个序列。

**可修复性**：**中等**。需要修改 Cowrie 的 `shell/protocol.py`，去掉这两个序列。

---

#### `fs.hostname_mismatch`（+15）

**检测方法**：对比三个来源

```bash
# 1. 提示符（PS1）
root@ubuntu-server:~#

# 2. hostname 命令
hostname          # → ubuntu-server

# 3. /etc/hostname
cat /etc/hostname # → svr04
```

**矛盾**：前两个说 `ubuntu-server`，第三个说 `svr04`。

**原理**：

- 提示符主机名 和 `hostname` 命令的输出，都来自 `cowrie.cfg` 的 `[honeypot] hostname = ubuntu-server`
- `/etc/hostname` 的内容来自 `fs.pickle` 的静态快照（`svr04`）

两者完全独立，管理员改一个不会同步另一个。

**为什么是强信号**：真实系统上这三者由同一个内核 hostname 驱动，不可能不同。

**可修复性**：**容易**。统一 `cowrie.cfg` 的 `hostname` 与 fs.pickle 里的 `/etc/hostname`。

---

#### `fs.container_markers`（+15）

**检测方法**：

```bash
ls -la /.dockerenv     # → -rwxr-xr-x ... 0 2026-05-04 14:44 .dockerenv
ls -la /proc/docker    # → 存在
```

**原理**：Cowrie 自带的 `fs.pickle` 是用 `bin/createfs` 从一个**真实的 Docker 容器**里抓取的。容器的特有标记（`/.dockerenv`、`/proc/docker`、`/var/log/runit`）被一起带进了假文件系统。

**为什么讽刺**：这台"物理服务器"同时声称自己是 Debian 服务器，却在根目录挂着容器标记。

**可修复性**：**容易**。重新生成 fs.pickle 时排除这些路径。

---

#### `cmd.head_numeric_shorthand`（+18）/ `cmd.tail_numeric_shorthand`（+12）

**检测方法**：

```bash
head -3 /etc/passwd
tail -2 /etc/passwd
```

**实测结果**：

```
head: invalid option -- '3'
tail: invalid option -- '2'
```

**原理**：`head -3 file` 是 POSIX 与 GNU coreutils 都支持的写法（数字简写）。Cowrie 的模拟器只认 `head -n 3`。

**为什么是强信号**：一个真实的 `head` 二进制不会拒绝 `-3`。这说明解析器是自己写的。

**可修复性**：**中等**。需要修改 `commands/ls.py` 等模块的参数解析逻辑。

---

#### `cmd.missing_modern_tools`（+15）

**检测方法**：

```bash
which ss ip systemctl
```

**实测结果**：无输出（三个都不存在）。

**原理**：

| 工具 | 引入时间 | 说明 |
|---|---|---|
| `ip` / `ss` | 2001 年（iproute2） | 替换 `ifconfig` / `netstat` |
| `systemctl` | 2015 年（systemd） | Ubuntu 15.04 起默认 |

banner 声称是 Debian 12（2023 年发布），却缺少这两个 8 年前就该有的组件。

**可修复性**：**中等**。需要为这些命令补充 Python 实现。

---

#### `fs.sshd_config_empty`（+12）/ `cmd.top_crash`（+12）

`sshd_config` 为空：假文件系统只建了路径没填内容。真实的 SSH 服务器必然有非空配置。

`top` 崩溃：Cowrie 的 `top` 依赖预置的 `/proc` 数据，遇到 `-n 1` 这种参数组合会走进未处理的代码路径，报 `E82: Cannot allocate any buffer`。

---

### 7.3 弱信号

弱信号单独看可能是配置差异，需要多条同时命中才有说服力。

| 检测项 | 权重 | 说明 |
|---|---|---|
| `cmd.uptime_short` | +10 | Cowrie 的 uptime 从进程启动算，不是从系统启动算 |
| `fs.uniform_timestamps` | +10 | 快照生成导致大量条目共享 mtime，去重率仅 18% |
| `proto.legacy_rsa_hostkey` | +8 | 只宣告 `ssh-rsa`，无 `rsa-sha2-*` |
| `cmd.legacy_nic_name` | +8 | `ifconfig` 硬编码 `eth0`，现代系统用 `enp0s3` |
| `cmd.kernel_distro_mismatch` | +8 | uname 说 Debian，目录结构却是容器快照 |
| `term.no_bracketed_paste` | +6 | 缺少现代 bash 的 bracketed paste 序列 |

## 八、防御方视角：如何把指数降到最低

> 这一章是给"想让蜜罐更真实"的部署者看的。它同时说明了识别器的价值——**只有能量化，才能优化**。

### 8.1 可修复性分级

| 层次 | 当前得分 | 可降到 | 难度 |
|---|---|---|---|
| 文件系统层 | 50 | ~0 | 低（重新生成 fs.pickle） |
| 命令行为层 | 88 | ~20 | 中（补充命令实现） |
| 终端行为层 | 21 | ~6 | 中（改 protocol.py） |
| 协议层 | 87 | ~50 | 极高（换 SSH 栈） |
| 认证层 | 30 | 0（但蜜罐失效） | 不可修复 |

### 8.2 推荐改造顺序

**第一步：统一身份（消除最便宜的破绽）**

```ini
# etc/cowrie.cfg
[honeypot]
hostname = svr04          # 与 fs.pickle 里 /etc/hostname 一致
```

**第二步：重新生成 fs.pickle**

用 `bin/createfs` 从一个内容可控的 rootfs 目录生成，注意：

- 排除 `/.dockerenv`、`/proc/docker`、`/var/log/runit`
- 正确填充 `/etc/os-release`（非空普通文件）
- 正确填充 `/etc/ssh/sshd_config`
- 打散 mtime（用 `touch -d` 随机化）

**第三步：补齐命令实现**

优先级：

1. `head` / `tail` 的数字简写（改 `commands/base.py` 的解析）
2. `df`、`sed` 的 Python 实现
3. `ss`、`ip`、`systemctl` 的桩实现

**第四步：去掉终端痕迹**

修改 `shell/protocol.py`，去掉输出前后的 `ESC[4l` / `ESC[4h`。

**第五步（唯一硬伤）：SSH 协议栈**

Cowrie 的算法集由底层 SSH 库决定，`cowrie.cfg` 只能裁剪不能扩充。要真正修复必须：

- 换用支持现代算法的 SSH 库（如直接基于 `cryptography` + 自实现握手），或
- 在 Cowrie 前面套一层真实 OpenSSH 做 TLS 终结式转发（改变架构）

**这就是为什么第八章开头说"极难"。** 协议层是 Cowrie 的架构性痕迹。

### 8.3 改造后的预期

基于上表估算，**完整改造后暴露指数可从 100 降到约 55–65**，仍会被判定为"高度可疑"但跌出"确定是蜜罐"区间。

这个结果符合项目初期的判断：**蜜罐可以被做得更难识别，但中等交互蜜罐的原理决定了它无法完全隐形**。原因很简单——它必须暴露一个可交互的假系统，而假系统必然与真系统有偏差。

### 8.4 一个重要的认识

**降低暴露指数的收益是递减的。**

把指数从 100 降到 60，成本可能只有几小时（改配置 + 重新生成 fs.pickle）；从 60 降到 40，成本是数周的开发（补全命令实现 + 改 protocol）；从 40 降到 20，需要重写 SSH 栈。

真实的安全运营中，**大多数部署会选择"够用就好"**：把最容易识破的破绽补上，然后靠**网络隔离**和**日志外送**来承担责任，而不是追求完美的伪装。这也是本项目在威胁分析中得出的核心结论之一（见第九章）。

## 九、威胁分析链条：本项目的完整评估记录

> 这一章记录项目过程中对 Cowrie 威胁面的系统性排查。每一条都做了实测验证，结论均为"不成立"，但原因各不相同。

### 9.1 威胁 1：从蜜罐内部逃逸到主机

**假设**：攻击者能否从 Cowrie 的模拟 shell 里跳出，拿到真实主机的控制权？

**验证**：

- 全部 57 个命令模块中，`eval()` / `exec()` / `os.system` / `subprocess` 出现 0 次（仅 2 处无害的 `subprocess.run(["which",...])` 和 `["clear"]`，不在攻击路径上）
- `gcc` 生成的是随机字节，不调用编译器
- `scp` / `sftp` 上传写入 `avatar.server.fs`（内存中的 pickle 树），不是真实磁盘
- `python` / `perl` / `bash` 命令输出预置文本，不启动解释器
- 蜜罐进程 `CapEff = 0000000000000000`（无任何 capability）

**结论**：**不成立**。Cowrie 没有代码执行路径，这是架构决定的。

**备注**：Bunyan/pickle 反序列化（`fs.pickle` 的 `__reduce__`）是理论风险，但替换该文件需要 uid 1001 写权限，构成循环依赖。

### 9.2 威胁 2：从主机横向移动到内网

**假设**：攻陷蜜罐主机后，能否以此为跳板攻击内网其他机器？

**验证**（网络层，VM 直接发起 TCP）：

| 目标 | 结果 |
|---|---|
| 公网 `example.com:80` | ✅ 通 |
| `192.168.122.1:22`（宿主机 virbr0） | ❌ closed |
| `192.168.122.1:53` | ❌ closed |
| `192.168.1.x`（真实局域网） | ❌ 不通 |
| `172.17.0.1`（docker0） | ❌ closed |

**结论**：**不成立**（当前配置下）。libvirt 的 NAT 与宿主机 firewalld 共同隔离了 VM。

**重要提醒**：这种隔离是**隐式的**——依赖宿主机防火墙的默认策略，而非 VM 自身的显式规则。一旦防火墙规则变化，这层保护就消失，而 VM 对此毫无感知。建议在 `nwfilter` 里显式声明出向规则，把"碰巧安全"变成"声明安全"。

### 9.3 威胁 3：利用已知 CVE

**假设**：Cowrie 有没有可利用的公开漏洞？

**验证**：

- 唯一公开 CVE：**CVE-2025-34469**（DoS，影响 ≤ 3.0.13）
- 本组版本：3.0.13，但**已打补丁**（代码中存在 `outbound_rate_limiter()` 工厂函数与 `[shell] *_rate_limit_*` 配置项，这是补丁的结构特征，上游未变更版本号）

**结论**：**不成立**。且 DoS 本身不提供代码执行。

### 9.4 威胁 4：作为 Botnet 节点

**假设**：既然蜜罐能访问公网，能否被招募为 botnet 节点？

**验证**：

| Botnet 节点的必要条件 | 蜜罐的实际状态 |
|---|---|
| 代码执行 | ❌ 不存在（见 9.1） |
| 持久化 | ❌ 无 systemd 服务、无 cron 任务 |
| C2 通道 | ⚠️ 理论通路（output 插件），但 URL 来自配置文件 |

**关键澄清**：`wget` 是 Python 模拟的，它调用 Twisted 的 `Agent`/`connectTCP`，下载的文件**存进 `downloads/` 目录，从不执行**。"蜜罐能出网"的含义是"**Cowrie 这个 Python 进程能出网**"，不是"**你能在这台机器上跑东西**"。

**结论**：**不成立**。

### 9.5 威胁 5：作为 DDoS 放大器

**假设**：能否利用蜜罐的出网能力发起 DDoS？

**验证**：

| 维度 | DDoS 需要的 | Cowrie 的实际限制 |
|---|---|---|
| 并发 | 数万同时连接 | 会话内命令串行执行（`cmdstack` 是栈） |
| 速率 | 数十万 PPS | `outbound_rate_limiter`：**每主机每 60 秒 5 次** |
| 时长 | 持续数小时 | `idle_timeout = 180` 秒 |
| 后端 | 数百个会话 | 配置中没有 `max_connections` |

**峰值攻击力估算**：

```
5 次/60 秒/主机 × N 个并发会话 = 5N/60 次请求/秒
```

即使开 100 个会话（已经会导致蜜罐自身失去响应），峰值约 **8 RPS**。真实 UDP 反射攻击可达数十万 PPS。

**额外的结构障碍**：速率限制按"目的主机"计数，不是按会话。所以多开会话打同一目标共享配额；想绕过必须换目标——那就不是 DDoS 了。

**结论**：**不成立**。技术上能发出连接，但攻击力比一台家用路由器还低。

### 9.6 威胁 6：利用 output 插件作为出站通道

**假设**：13 个 output 插件直接 `Agent.request()`，不经过 `_is_blocked` 黑名单，能否被利用？

**验证**：

```python
# output/discord.py:52
self.url = CowrieConfig.get("output_discord", "url").encode("utf8")  # 完全由配置决定
self.agent = client.Agent(reactor)
d = self.agent.request(b"POST", self.url, headers, body)             # 不过 _is_blocked
```

**覆盖面澄清**：

| 路径 | 是否检查 `_is_blocked` |
|---|---|
| `curl` / `wget` / `nc` / `ftpget` / `tftp` | ✅ 检查 |
| 13 个 output 插件（axiom/cuckoo/datadog/discord/dshield/graylog/greynoise/malshare/signal/splunk/telegram/urlhaus/virustotal） | ❌ 不检查 |
| `[llm] host`（默认 `https://api.openai.com`） | ❌ 不检查 |

**结论**：**部分成立，但攻击者不可控**。URL 来自配置文件，攻击者改不了配置（需要 uid 1001）。这**不是攻击者能主动利用的洞，而是配置错误的后果**。

**真正的风险**：如果管理员把某个 webhook 指向被攻陷的域名，蜜罐会**主动、周期性地**往那里发数据。这是一个"配置驱动的出站通道"。

**由此得出的安全建议**：蜜罐主机必须严格控制**谁能写配置文件**——配置文件的写权限就是权限边界。

### 9.7 威胁分析总结

| 威胁 | 结论 | 根本原因 | 可修复性 |
|---|---|---|---|
| 逃逸到主机 | ❌ 不成立 | 无代码执行路径 | 架构决定 |
| 横向到内网 | ❌ 不成立 | 网络隔离 | 隐式，建议显式化 |
| 已知 CVE | ❌ 不成立 | 唯一 CVE 已修补 | —— |
| Botnet 节点 | ❌ 不成立 | 无代码执行 + 无持久化 | 架构决定 |
| DDoS 放大器 | ❌ 不成立 | 速率限制 + 串行执行 | 架构决定 |
| Output 插件出站 | ⚠️ 部分成立 | 配置驱动，非攻击者可控 | 权限管理 |

**真正的风险面不在这六条里，而在部署配置**：

1. **蜜罐主机上存在独立于蜜罐的真实 SSH 服务**，且账号凭据与管理通道复用
2. **Cowrie 的代码、配置与日志由运行蜜罐的同一 uid 拥有且 group-writable**（实测：`cowrie.cfg`、全部 57 个 `.py`、`cowrie.json` 都属于 `cowrie:cowrie`，权限 `-rw-rw-r--`）
3. **蜜罐进程未启用 `NoNewPrivs` / seccomp**（实测 `NoNewPrivs: 0`、`Seccomp: 0`）
4. **日志可被篡改** —— 蜜罐的全部产出是日志，它变成可写等于"证据可以被销毁"

## 十、局限性与已知误差

### 10.1 检测器的局限

**1. 依赖默认配置**

部分检测项（如 `/etc/os-release` 为空、`/.dockerenv` 存在）依赖 Cowrie 自带的 `fs.pickle`。如果部署者重新生成过文件系统，这些项会失效。

**2. 无法识别高交互蜜罐**

高交互蜜罐运行真实系统，本项目的文件系统层和命令行为层检测全部不适用。识别高交互蜜罐需要网络流量分析、业务逻辑分析等手段。

**3. 认证层检测会留下日志**

`auth.accepts_random_password` 需要一次真实登录尝试，会在 Cowrie 的 `cowrie.json` 里留下 `cowrie.login.success` 记录。防守方可以通过这条记录发现"有人在识别蜜罐"。

**4. 协议层检测需要建立 TCP 连接**

即使 `--passive` 模式也会留下 `cowrie.session.connect` 记录。

**5. 弱信号存在误报可能**

`cmd.uptime_short` 对刚重启的真实系统会误报（本项目对照组就命中了这一条）。这是设计上的取舍：宁可误报一条弱信号（+10），也不漏掉真实的短期运行迹象。

### 10.2 已知的实现细节

**1. `remote_kex_init` 的场景差异**

paramiko 5.x 在一次认证握手后会清空 `remote_kex_init`。本项目改用原始 TCP 读取，规避了这个问题，但也意味着算法集探测独立于 paramiko 的会话。

**2. `--passive` 模式不完整**

`--passive` 跳过 shell 会话，但 `proto.no_exec_channel` 检测仍需一次登录。若登录失败（凭据错误），该检测项记为"未参与判定"而不是"正常"。

**3. 提示符解析依赖 PS1 格式**

`_remember_prompt` 用正则 `([A-Za-z0-9_.-]+)@([A-Za-z0-9_.-]+):` 解析提示符。如果部署者修改了 PS1 格式，主机名对比会失效。

### 11.4 终端字节流对照

```

  b'whoami\r\n\x1b[?2004l\r\x1b]3008;start=<uuid>;...\x1b\\ubuntucowrie\r\n'

```

- Cowrie 有 `ESC[4l` / `ESC[4h`，真实 bash 没有

- 真实 bash 有 `OSC 3008`（会话标记）和 `OSC 0`（窗口标题），Cowrie 没有

## 结语

这个项目的价值不在于"写了一个能认出 Cowrie 的脚本"——那部分只需要照着一个已知蜜罐的字符串匹配就能做到。

价值在于**建立了一套可复用的分析框架**：

1. **分层**：把"伪装"拆成五个独立的攻击面，每层单独评估
2. **分级**：把证据按强度分级，避免单条弱信号导致的误报
3. **量化**：给出可对比的分数，让"改造前 / 改造后"成为可度量的工程指标
4. **可解释**：每条检测项都能说明"为什么这不可能出现在真实系统上"，而不是黑盒判定

这套框架同样适用于评估其他蜜罐产品、审视自动化系统的行为一致性，以及理解"模拟与真实的差距在哪里"——而这正是本次作业的核心主题。
