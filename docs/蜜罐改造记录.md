## 一、目标与方法

### 1.1 目标

把蜜罐的"暴露指数"（见《蜜罐识别器设计与检测报告》）尽可能压低，让 `honeypot_detect.py` 更难判定它是蜜罐。

项目初期设定的现实目标是：**把决定性信号清零，把指数压到"高度可疑"以下**，而不是追求完全隐形。

### 1.2 测量方法

每一步改造后都跑一次完整检测，记录：

| 指标 | 含义 |
|---|---|
| **指数** | 0–100，`honeypot_detect.py` 的正式评分（封顶 100） |
| **原始分** | 未裁剪的权重总和 —— 改造过程中指数会撞上 100 的天花板，原始分才能反映真实进展 |
| **D / S / W** | 决定性 / 强信号 / 弱信号的命中数量 |
| **分层小计** | 协议层 / 认证层 / 文件系统层 / 命令行为层 / 终端行为层的各自得分 |

测量命令：

```bash
./tools/measure.sh step06_commands_full
```

每次结果存在 `reports/<标签>.json`，可随时对比。

### 1.3 一个重要的方法论问题

**指数在改造前期完全没有变化（一直是 100）。** 这是因为评分模型有"决定性项兜底"规则：任一决定性项命中，指数至少 70；而蜜罐有 4 条决定性项，原始分远超 100。

如果只看指数，前 5 步的改进全部"看不见"。这正是我们后来加入"原始分"指标的原因 —— **可观测的指标必须能反映真实的改进，否则改造就变成了盲目的**。

这个问题本身也值得记录：任何"评分体系"都会遇到天花板效应，设计时必须同时提供一个不封顶的辅助指标。

## 二、改造总览：分数曲线

| 步骤 | 改造内容 | 指数 | 原始分 | D | S | W | 分层（协议/认证/文件/命令/终端） |
|---|---|---|---|---|---|---|---|
| 基线 | 原始状态 | 100 | **313** | 4 | 12 | 6 | 82 / 30 / 62 / 118 / 21 |
| 1 | 统一主机名 | 100 | 313 | 4 | 12 | 6 | 82 / 30 / 62 / 118 / 21 |
| 2 | 重建假文件系统 | 100 | **243** | 3 | 10 | 4 | 82 / 30 / **0** / 110 / 21 |
| 3 | 去掉终端控制序列 | 100 | **228** | 3 | 9 | 4 | 82 / 30 / 0 / 110 / **6** |
| 4 | 实现 df 命令 | 100 | **178** | 2 | 7 | 4 | 82 / 30 / 0 / **60** / 6 |
| 5 | 修正 uptime 与网卡名 | 100 | **160** | 2 | 7 | 2 | 82 / 30 / 0 / **42** / 6 |
| 6 | 补全 sed/top/ss/ip/systemctl | 100 | **118** | 1 | 5 | 2 | 82 / 30 / 0 / **0** / 6 |

**总计：原始分从 313 降到 118，降幅 62%。**

### 2.1 各层降幅

| 层 | 基线 | 最终 | 降幅 | 说明 |
|---|---|---|---|---|
| 文件系统层 | 62 | **0** | 100% | 完全消除 |
| 命令行为层 | 118 | **0** | 100% | 完全消除 |
| 终端行为层 | 21 | 6 | 71% | 剩 1 项架构性缺陷 |
| 协议层 | 82 | 82 | 0% | **无法降低** |
| 认证层 | 30 | 30 | 0% | **设计使然** |

### 2.2 为什么指数一直是 100

因为评分模型规定"决定性项命中则指数 ≥ 70"，而认证层那条决定性项（接受任意随机密码）**不可能消除** —— 它是蜜罐的定义性特征。

所以**指数永远不会降到 70 以下**，除非放弃蜜罐功能。这一点在第五章会再展开。

## 三、逐步详解

### 步骤 1：统一主机名

**问题**

同一台机器有三个"名字"，互不相同：

```bash
$ hostname               # ubuntu-server   ← 来自 cowrie.cfg
root@ubuntu-server:~#    # ubuntu-server   ← 提示符，同样来自 cowrie.cfg
$ cat /etc/hostname      # svr04           ← 来自 fs.pickle
```

真实系统上这三者由同一个内核 hostname 驱动，不可能不同。

**改法**

```ini
# etc/cowrie.cfg
[honeypot]
hostname = svr04
```

**效果**

- 消除 1 条强信号（`fs.hostname_mismatch`，15 分）
- 原始分 313 → 313（该检测项同时被其他信号掩盖，分值体现在强信号计数 13→12）

**这个结果说明**：单独修一条分值不高的项，在总分封顶的情况下看不出变化。这是后面引入原始分指标的触发点。

---

### 步骤 2：重建假文件系统（最大的一步）

**问题**

Cowrie 的 `fs.pickle` 是从一个 **Docker 容器**里抓的快照，导致三类破绽：

| 破绽 | 具体表现 |
|---|---|
| 内容缺失 | `/etc/os-release` 是空目录（`cat` 无输出，`ls` 显示 267 字节） |
| 内容缺失 | `/etc/ssh/sshd_config` 存在但为空 |
| 快照痕迹 | `/.dockerenv`、`/proc/docker`、`/var/log/runit` 都在 |
| 快照痕迹 | 根目录 22 个条目只有 4 个不同 mtime（去重率 18%） |
| 身份矛盾 | `/etc/passwd` 里有 `phil` 用户和 `vboxsf` 组（VirtualBox 痕迹） |

**改法**

`tools/rebuild_fs.py` 直接操作 pickle 的节点树：

```bash
python3 tools/rebuild_fs.py <源 fs.pickle> <输出 fs.pickle>
```

节点格式（10 元位置列表）：

```
[name, type, uid, gid, size, mode, ctime, contents, target, realfile]
```

脚本做了 6 件事：

1. **修正发行版标识** —— 写入完整的 Debian 12 `os-release`，新增 `lsb-release`、`debian_version`
2. **统一主机名** —— `hostname`、`hosts`、`motd` 全部改为 `svr04`
3. **替换用户数据库** —— 用干净的 Debian 12 `passwd` / `group`，移除 `phil` / `vboxsf`，新增 `deploy` 管理员及其家目录
4. **填充 sshd_config** —— 写入完整的 Debian 12 默认配置（保留 `PermitRootLogin prohibit-password`，这样"root 能登录"在文件系统层面也自洽）
5. **删除容器痕迹** —— `/.dockerenv`、`/proc/docker`、8 处 runit 路径
6. **打散时间戳** —— 根目录 19 个条目的 mtime 随机分布在 540 天内（固定随机种子，结果可复现）

**效果**

| 指标 | 变化 |
|---|---|
| 文件系统层 | 62 → **0** |
| 原始分 | 313 → **243** |
| 决定性项 | 4 → 3（`os-release` 那条消除） |
| 强信号 | 12 → 10 |

**这是性价比最高的一步**：一次改造清空了整个文件系统层（62 分）。

**注意**：重建后的身份是 **Debian 12 + svr04**，与 `cowrie.cfg` 里 `[shell] kernel_version = 6.1.0-21-amd64` 一致。如果以后想换成 Ubuntu 身份，改脚本顶部的常量即可。

### 步骤 3：去掉终端控制序列

**问题**

Cowrie 在每条命令前后插入终端控制序列：

```
$ echo TEST
b'echo TEST\r\n\x1b[4lTEST\r\n\x1b[4hroot@svr04:~# '
                 ^^^^^^^^      ^^^^^^^^
```

`ESC[4l` = 关闭插入模式，`ESC[4h` = 开启插入模式。**真实 bash 不会主动发送这两个序列。**

**定位过程（值得记录的排查）**

一开始在 Cowrie 源码里搜遍 `4l` / `4h` 都没有结果，改用 monkeypatch 追踪调用栈才找到：

```
cowrie/shell/honeypot.py:947  HoneyPotShell.resume()
  → self.protocol.setInsertMode()
    → twisted/conch/recvline.py:406  terminal.setModes([insults.modes.IRM])
      → twisted/conch/insults/insults.py:713  write(b"\x1b[4h")

cowrie/shell/protocol.py:513  call_command()
  → self.setTypeoverMode()
    → twisted/conch/recvline.py:410  terminal.resetModes([IRM])
      → insults.py:723  write(b"\x1b[4l")
```

**改法**

在 `cowrie/shell/protocol.py` 的 `HoneyPotInteractiveProtocol` 里覆盖这两个方法。

**踩到的坑（重要）**

第一次尝试把方法覆盖成**完全空操作**：

```python
def setInsertMode(self) -> None:
    """屏蔽 ESC[4h"""
```

结果 shell 直接崩溃：

```
AttributeError: 'HoneyPotInteractiveProtocol' object has no attribute 'mode'
```

原因：这两个方法除了发序列，还维护 `self.mode`（"insert" / "typeover"），而 `characterReceived()` 依赖它决定插入还是覆盖字符。

**正确写法**是保留状态、只去掉序列：

```python
def setInsertMode(self) -> None:
    self.mode = "insert"        # 保留状态

def setTypeoverMode(self) -> None:
    self.mode = "typeover"      # 保留状态
```

**第二个坑**：补丁第一次被插进了 `HoneyPotExecProtocol`（错误位置），因为那个类里也有同名方法。修正后的脚本会验证插入位置的所属类。

**第三个坑**：改完 `.py` 后必须清 `__pycache__` 并重启，否则加载的仍是旧字节码。第一次改完测试无效，就是因为进程用的是缓存的 `.pyc`。

**效果**

```
改造前：b'echo TEST\r\n\x1b[4lTEST\r\n\x1b[4hroot@svr04:~# '
改造后：b'echo TEST\r\nTEST\r\nroot@svr04:~# '
```

| 指标 | 变化 |
|---|---|
| 终端行为层 | 21 → **6** |
| 原始分 | 243 → **228** |

### 步骤 4：实现 df 命令

**问题**

```bash
$ df -h
-bash: /usr/bin/df: cannot execute binary file: Exec format error
```

原因：Cowrie 没有 `commands/df.py`，只在 `data/txtcmds/bin/df` 放了一段静态文本。txtcmd 机制不接受参数，某些参数形式会掉进"通用二进制"回落路径。

`df` 属于 coreutils，所有 Linux 发行版必备 —— 这是**决定性信号**。

**改法**

新建 `tools/cowrie_commands/df.py`，完全按 Cowrie 官方命令模块的写法：

```python
commands = {}

class Command_df(HoneyPotCommand):
    def call(self) -> None:
        ...

commands["df"] = Command_df
commands["/bin/df"] = Command_df
commands["/usr/bin/df"] = Command_df
```

实现范围：`-h` / `-H` / `-T` / `-a` / `-i` / `-P` / `--help` / `--version`，以及任意路径参数。

输出的分区表与 fs.pickle 的设定一致（20G 根分区）。

**注册方式**

不能直接改 `commands/__init__.py` 的列表（容易破坏格式），而是用 `tools/register_cmd.py` 按字母序插入：

```bash
python3 tools/register_cmd.py df
```

**效果**

```
$ df -h
Filesystem                    Size    Used   Avail  Use% Mounted on
tmpfs                         200M      1M    199M   0%  /run
/dev/sda1                      20G    4.3G     16G  21%  /
tmpfs                        1000M       0   1000M   0%  /dev/shm
tmpfs                           5M       0      5M   0%  /run/lock
/dev/sda15                    105M      6M     99M   6%  /boot/efi
```

| 指标 | 变化 |
|---|---|
| 命令行为层 | 110 → **60** |
| 原始分 | 228 → **178** |
| 决定性项 | 3 → 2（`df` 那条消除） |

### 步骤 5：修正 uptime 与网卡名

**问题 A：uptime 永远显示"刚开机"**

```bash
$ uptime
 02:10:44  up 10 min,  1 user,  load average: 0.00, 0.00, 0.00
```

原因在 `cowrie/shell/protocol.py`：

```python
def uptime(self):
    pt = self.getProtoTransport()
    return time.time() - pt.factory.starttime     # ← Cowrie 进程的启动时刻
```

每次重启蜜罐，uptime 都归零。生产服务器极少在 1 小时内重启。

**改法**

```python
offset_days = CowrieConfig.getint("honeypot", "uptime_offset_days", fallback=47)
boot_time = pt.factory.starttime - offset_days * 86400
return time.time() - boot_time
```

**问题 B：ifconfig 硬编码 eth0**

```bash
$ ifconfig
eth0      Link encap:Ethernet  HWaddr ...
```

systemd 的 `net.ifnames` 自 2015 年起默认启用可预测网卡名（`enp0s3`、`ens33`），现代 Debian/Ubuntu 不再使用 `eth0`。

而且 `ip a` 显示的是 `enp1s0`（我新写的实现），`ifconfig` 显示 `eth0`，**两个命令互相矛盾**。

**改法**

把网卡名改成从配置读取：

```python
nic_name = CowrieConfig.get("honeypot", "nic_name", fallback="enp1s0")
```

**踩到的坑**

改完后 `ifconfig` 直接报错：

```
NameError: name 'CowrieConfig' is not defined
```

`ifconfig.py` 没有导入 `CowrieConfig`。补上导入即可（用 `tools/add_import.py`）。

**效果**

```
$ uptime
04:18:30  up 47 days,  0:00,  1 user,  load average: 0.00, 0.00, 0.00

$ ifconfig
enp1s0    Link encap:Ethernet  HWaddr 2d:f6:9a:e3:a7:3e
          inet addr:192.168.122.252  Bcast:192.168.122.255  Mask:255.255.255.0
```

| 指标 | 变化 |
|---|---|
| 命令行为层 | 60 → **42** |
| 原始分 | 178 → **160** |
| 弱信号 | 4 → 2 |

### 步骤 6：补全 sed / top / ss / ip / systemctl

**问题**

| 命令 | 原状态 |
|---|---|
| `sed` | 未实现 → `cannot execute binary file` |
| `top` | txtcmd 只有一行 `E82: Cannot allocate any buffer, exiting...` |
| `ss` / `ip` / `systemctl` | 完全不存在 → `command not found` |

`sed` 是 POSIX 必备，`ip`/`ss` 自 2001 年、`systemd` 自 2015 年起是默认组件。一个声称是 Debian 12 的系统不可能缺这些。

**改法**

新建 `tools/cowrie_commands/sed.py` 和 `systemtools.py`（后者含 top / ss / ip / systemctl 四个类）。

**sed 的实现范围**（不是完整实现）：

```
sed -n 1p file          打印第 1 行
sed -n 1,5p file        打印 1-5 行
sed 's/a/b/' file       替换第一个
sed 's/a/b/g' file      替换全部
sed -n '/pat/p' file    打印匹配行
sed '1,3d' file         删除 1-3 行
```

不支持的东西会明确报错，而不是静默失败。

**为什么不用真 sed**：蜜罐的设计前提就是"不执行真实二进制"。真调用 `/usr/bin/sed` 会同时暴露宿主机工具链并失去日志能力。

**删除 top 的 txtcmd**

```bash
rm -f $P/data/txtcmds/usr/bin/top
```

否则 txtcmd 优先级高于 Python 实现，仍然返回那行错误。

**补齐假文件系统的路径**

新命令虽然有 Python 实现，但 `which` / `ls /usr/bin` 依赖 fs.pickle 的目录树。补完后：

```bash
$ which ss ip systemctl
/usr/bin/ss
/bin/ss
/usr/sbin/ip
...
```

路径重复是因为 `PATH` 里同时有 `/bin` 和 `/usr/bin`，而 fs.pickle 里 `/bin` 是指向 `usr/bin` 的符号链接 —— **真实 Debian 12 的行为也是如此**，所以这个输出是正确的。

**效果**

```
$ top -n 1
top - 04:25:12 up 47 days,  0:00,  1 user,  load average: 0.00, 0.01, 0.00
Tasks: 128 total,   1 running, 127 sleeping,   0 stopped,   0 zombie
...

$ ss -tulnp
Netid  State        Recv-Q  Send-Q Local Address:Port   Peer Address:Port  Process
tcp    LISTEN            0     128 0.0.0.0:22           0.0.0.0:*          users:(("sshd",pid=462,fd=3))

$ systemctl status ssh
● ssh.service - OpenBSD Secure Shell server
     Loaded: loaded (/lib/systemd/system/ssh.service; enabled; preset: enabled)
     Active: active (running) since Tue 2025-09-09 03:41:15 UTC; 47 days ago
   Main PID: 462 (sshd)
```

| 指标 | 变化 |
|---|---|
| 命令行为层 | 42 → **0** |
| 原始分 | 160 → **118** |
| 强信号 | 7 → 5 |

## 四、剩余分项分析：为什么降不下去

改造后剩余 118 分，全部来自协议层（82）和认证层（30），以及终端层的一项（6）。

### 4.1 认证层：30 分，不可消除

```
[命中] 接受任意随机密码  (+30)
```

**这是蜜罐的定义性特征。** 蜜罐必须让攻击者进来，否则无法收集情报。如果改成只接受正确密码，攻击者进不来，蜜罐就退化成一个普通 SSH 服务。

**唯一的"改善"方式是改变执行方式**：把 Cowrie 放到一台根本不打算被攻破的高交互环境里，或者接受"认证层必然暴露"这个事实。

**结论：这 30 分应当保留。** 报告中应明确说明——这不是缺陷，是设计取舍。

### 4.2 协议层：82 分，架构性上限

六项全部来自 Twisted 的 SSH 栈：

| 检测项 | 分值 | 能否消除 |
|---|---|---|
| 未提供任何 AEAD 密码 | 16 | ❌ |
| 提供已废弃的 CBC | 14 | ✅ 部分（减少宣告） |
| 未提供 ETM MAC | 14 | ❌ |
| 提供 hmac-md5 | 12 | ✅ 部分 |
| 仅 ssh-rsa host key | 8 | ✅ 部分 |
| 不支持 exec 通道 | 18 | ❌ |

**实测确认了 Twisted 的真实能力边界**：

```python
transport._getSupportedCiphers()
→ ['aes256-ctr', 'aes256-cbc', 'aes192-ctr', 'aes192-cbc',
   'aes128-ctr', 'aes128-cbc', '3des-cbc']
```

**Twisted 根本没有实现 chacha20-poly1305 或 AES-GCM。** 所以 `cowrie.cfg` 的 `ciphers` 只能**裁剪**（少宣告几个），不能**扩充**。

**可以做的裁剪**（约能降 34 分）：

```ini
[ssh]
# 只保留 CTR 模式，去掉全部 CBC
ciphers = aes128-ctr,aes192-ctr,aes256-ctr
# 去掉 hmac-md5 与 hmac-sha1
macs = hmac-sha2-512,hmac-sha2-384,hmac-sha2-256
```

**但这样做有个反效果**：真实 Debian 12 的 SSH 会宣告 AEAD 算法，我们把 CBC 删掉后仍然没有 AEAD，反而更像"被手工裁剪过的服务端"。**裁剪能降低检测器的分数，但不会提高真实度。**

这是本项目的一个重要结论：**检测分数和真实度不完全等价**。刻意针对检测器优化，可能得到"检测器认不出、但真人一看就觉得不对劲"的结果。

**因此这一步我们没有执行**，把它作为分析结论写进报告，而不是当成改造手段。

### 4.3 终端层：6 分，可接受

```
[命中] 缺少 bracketed paste 模式序列  (+6)
```

现代 bash（5.0+）会发送 `ESC[?2004h` 启用 bracketed paste。Cowrie 的简化 shell 没有实现这个特性。

这一项被归为**弱信号**，单独看可能是用户自定义了 PS1 或关闭了该特性，不构成判定依据。**保留是合理的。**

### 4.4 最终判定状态

| 指标 | 值 |
|---|---|
| 暴露指数 | 100（封顶） |
| 原始分 | 118 |
| 判定 | "确定是蜜罐" |
| 决定性项 | 1（仅认证层） |
| 强信号 | 5（全部协议层） |
| 弱信号 | 2 |

## 六、结论

### 6.1 改造成果

| 维度 | 改造前 | 改造后 |
|---|---|---|
| 原始暴露分 | 313 | **118**（↓62%） |
| 决定性信号 | 4 条 | **1 条**（仅认证层） |
| 强信号 | 12 条 | **5 条**（全部协议层） |
| 弱信号 | 6 条 | **2 条** |
| 文件系统层 | 62 | **0** |
| 命令行为层 | 118 | **0** |
| 终端行为层 | 21 | **6** |

### 6.2 三个核心认识

**第一：中等交互蜜罐的伪装有明确的天花板。**

低成本的改造（重建文件系统、补命令实现）能消除 180 分，但再往下就是架构问题。协议层和认证层合计 112 分，都不是"配置"能解决的。

这印证了项目初期的判断：**中等交互蜜罐可以被做得更难识别，但无法完全隐形**，因为它必须暴露一个可交互的假系统。

**第二：检测分数不等于真实度。**

协议层那 82 分里，有约 34 分是可以通过"裁剪算法集"消掉的。但裁剪后的结果是"一个没有 AEAD、没有 ETM、也没有 CBC 的 SSH 服务端" —— 检测器给的分会更低，但稍有经验的攻击者会觉得更可疑，因为真实服务器不会这样配置。

**针对检测器优化 ≠ 提高真实度。** 这是安全工程中的常见陷阱：把指标当成目标。

**第三：认证层的暴露应该被接受，而不是修复。**

蜜罐的存在意义是"被攻破"。要求它"不暴露自己会接受任意密码"，等于要求它不要工作。

正确做法是**承认这一层**，把资源投入到其他层面，并在部署时用网络隔离、日志外送、独立主机来承担"被识破之后"的风险。

### 6.3 改造带来的实际收益

抛开分数，这次改造让蜜罐在几个方面真正变好：

1. **文件系统自洽** —— 攻击者看到的 `/etc/passwd`、`/etc/os-release`、`/etc/hostname` 互相一致，不再自相矛盾
2. **命令行为可信** —— 常用命令能正常执行，攻击者不会因为"df 跑不了"而立刻退出
3. **消除了容器痕迹** —— 不再暴露"这台服务器其实是 Docker 快照"这个致命破绽
4. **能支撑更真实的攻击模拟** —— 攻击者可以真正执行一次完整的侦察流程，产生的日志才有分析价值

**第 4 点最重要**：作业要求"收集有意义的攻击活动日志"。一个一眼就被识破的蜜罐，攻击者会立刻离开，日志里只有几行登录失败，分析章节根本写不出东西。
